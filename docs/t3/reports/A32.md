## 5. Sicherheit & Datenschutz

- **Kein Zugriff auf Stefans Helium-Profil.** Die Leiste arbeitet ausschließlich auf dem
  **eigenen Browser-Profil des Agenten** (`ensureAgentBrowserStarted(agentId)` /
  `getAgentComputerPrefs(agentId)`). Der Platzhalter sagt das dem Nutzer ausdrücklich:
  *„Der Browser läuft in seinem eigenen Profil — nicht in Stefans Helium."*
- **Keine Secrets im localStorage.** Gemerkt werden ausschließlich Modus und Breite
  (`connect.browser-dock`), keine Tokens, keine Profilpfade, keine Cookies.
- **Keine Tokens im Browser.** Der T3-Stream läuft über die Better-Auth-Session
  (`credentials: "include"`); der Bridge-Token bleibt serverseitig.
- **Kein Klick-/Tastatur-Forwarding** in die T3-Vorschau. Die Leiste ist Zuschauen + Adresse;
  die volle Steuerung bleibt im bestehenden Vollbild (`agent-chrome-fullscreen`). Damit kann die
  Leiste keinen Tastendruck in eine fremde Sitzung einspeisen.

### 6.2 Das Protokoll, das über die Brücke kommen müsste

`ServerBrowserStream.ts` schreibt Frames in zwei Formen:

- **Binär:** JPEG-Bilder (`case "frame"` → `writer.write(frame.data)`), mit
  `MAX_SOCKET_BUFFER_BYTES = 8 MiB` als Socket-Backpressure-Grenze. Jedes Bild hat eine `ack`,
  die Chromium erwartet — **der Client muss den Ack-Request beantworten**, sonst steht der
  Stream.
- **JSON:** alle übrigen Ausgaben als `{ type, ...data }` — die `_tag` wird zu `type` umbenannt:
  `viewport`, `control`, `clipboard`, `download`, `fileChooser`, `fileChooserClosed`, `popup`,
  `pointer`, `probe`.
- **Steuerung:** `case "gone"` beendet den Stream, `case "reconnect"` schließt mit
  `CloseEvent(1012, "reconnect")` — der Client muss sich dann neu verbinden.

Kernform des Control-Frames (aus `ServerBrowser.ts`):

```ts
{
  readonly _tag: "control";
  readonly canOperate: boolean;
  readonly controller: "agent" | "you" | "another-viewer" | "unclaimed";
  readonly generation: number;
  readonly dialog: { type, message, defaultValue } | null;
}
```

Der `controller`-Wert ist der **Besitzmarker**: `canOperate` + `controller` sagen, ob dieser
Viewer steuern darf. Das ist für Connect wichtig — zwei Viewer (Connect-Leiste und T3-Fenster)
dürfen sich nicht gegenseitig in die Hand arbeiten.

### 6.3 Metadaten (RPC, nicht Stream)

Über die WS-RPC von T3 (`packages/contracts/src/rpc.ts`, `packages/contracts/src/preview.ts`):

```
preview.open  preview.navigate  preview.resize  preview.adjust
preview.refresh  preview.close  preview.list
preview.clearProfile  preview.reportProfiles  preview.reportStatus
```

Der Zustand einer Vorschau liegt als `PreviewSessionSnapshot` vor:

```ts
{
  threadId, tabId, navStatus, canGoBack, canGoForward,
  viewport?, colorScheme?, zoomFactor?,
  profileId?, runtime?, automationOwner?, reveal?, revealRequest?,
  updatedAt
}
```

### 6.4 Was daraus für Connect folgt

**Sofort nutzbar über die Brücke:**

1. **Metadaten** (`preview.list` ⇒ Tabs mit URL, Titel, Zurück/Vorwärts-Möglichkeit). Das ist
   genau die Form, die `T3PreviewTab` in dieser Lane abbildet — der Typ existiert bereits, damit
   die Brücke später nur noch Daten liefern muss.
2. **Viewport** (`viewport`-Frame) — erlaubt eine maßstabsgetreue Darstellung in der Leiste
   statt `object-cover`.
3. **`control`-Frame** — erlaubt die Anzeige, *ob* Connect diesen Tab steuern darf
   (`canOperate`/`controller`), statt blind zu steuern.

**Was über eine Brücke kommen müsste, aber heute nicht vorhanden ist:**

| Wunsch | Ziel-Lane | Form |
|---|---|---|
| Preview-Stream durchreichen | **A37/A03** (Server) | Route `/api/t3/preview-stream/ws` (Wunsch-Route in `t3-preview-client.ts` hinterlegt), die den Sidecar-Stream proxyt. |
| `preview.list` als HTTP | **A37/A03** | `/api/t3/preview/sessions` (in `T3_PREVIEW_BRIDGE_ROUTE_HINTS` hinterlegt). |
| `navigate` / `refresh` | **A37/A03** | `/api/t3/preview/navigate`, `/api/t3/preview/refresh`. |
| Frame als `<img>`-URL | **A37/A03** | entweder MJPEG-Endpunkt oder ein serverseitiger JPEG-Proxy. **Wichtig:** T3 liefert Binärframes, die ein Browser-`<img>` nicht direkt laden kann — die Brücke muss daraus eine ladbare URL machen (oder Connect muss den WS-Stream direkt sprechen). |

**Ein Hinweis zur Brücken-Architektur:** Der T3-Sidecar läuft als eigener Dienst. Die Brücke
muss den Stream also **durchreichen** (Proxy), nicht T3 in Connect einbetten — T3s Preview-Stream
ist viewer-gebunden (genau ein Viewer bekommt den `control`-Besitz). Ein Proxy, der denselben
Stream an zwei Viewer hängt, würde das Besitzmodell brechen. Deshalb sollte die Brücke genau
**einen** Connect-Viewer bedienen und `canOperate` durchreichen.

### 7.1 Ein Hinweis zum Test-Setup (gefunden und behoben)

Beim Lauf im **Gesamtlauf** (`bun test apps/app/src`) fielen die Tests dieser Lane zunächst durch.
Ursache ist **nicht** die Lane, sondern die Test-Infrastruktur:

- Bun führt **alle** Testdateien in **einem** Prozess aus.
- Mehrere Dateien melden ihr happy-dom per `GlobalRegistrator.unregister()` wieder ab
  (`bot-avatar.test.tsx`, `browserSplit*.test.tsx`, `sparkOverview-design.test.tsx`,
  `controlToggleFlag.test.tsx`).
- `@/test/dom` (`ensureDom`) merkt das nicht: sein **Modul-Flag** bleibt auf „registriert",
  obwohl `document` in Wahrheit weg ist. Der nächste Aufrufer überspringt darum das Registrieren.
- Zusätzlich bindet `@testing-library/react` sein globales `screen` an das `document`, das beim
  **Import** der Bibliothek existiert. Wird sie vor dem DOM-Setup geladen, ist dieser Anker
  dauerhaft kaputt ⇒ alle nachfolgenden Dateien scheitern mit
  *„a global document has to be available"*.

Die Lane-Testdatei löst das selbst (ohne Änderung an fremden Dateien):
1. Sie prüft den **echten** DOM-Zustand statt dem Modul-Flag zu glauben und registriert bei
   Bedarf neu.
2. Sie lädt `@testing-library/react` **dynamisch** (`await import(...)`) — erst **nach** dem
   DOM-Setup. Damit ist der `screen`-Anker gültig.

Der Import von `@testing-library/react` muss also **nach** dem DOM-Setup erfolgen; das ist
notiert, damit die Datei nicht „aufräumt" und wieder bricht.
