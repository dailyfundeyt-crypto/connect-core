## 4. Sicherheit und Akzeptanzkriterien

### Kopplungs-Token läuft ab

- Standard-TTL **5 Minuten** (`DEFAULT_MOBILE_PAIRING_TTL_MS`), injizierbare Uhr für Tests.
- Test: Code bei `now = START` erzeugt, bei `START + 60_001 ms` eingelöst → `reason: "expired"`,
  HTTP **410**, keine Geräteanlage, `activeTickets: 0`.
- Abgelaufene Tickets bleiben eine Stunde für die korrekte Fehlermeldung erhalten und werden
  danach aus dem Speicher entfernt. Ein Neustart des Servers macht offene Codes ungültig
  (gewollt: kurzlebig, kein Persistieren von Klartext).

### Kein Token im Log

- `RedactedLogger` aus A10 ist vorgeschaltet; geloggt werden nur `ticketId`, `deviceId`,
  `expiresAt` und ein optionales Label.
- Token und Geräte-Credential werden **nie** an den Logger gegeben; die Pair-URL ebenfalls nicht.
- Test prüft: Token, Credential, `tokenHash`, `credentialHash` und die Pair-URL kommen weder in
  Logzeilen noch in `status`/`devices`-JSON vor.
- Das Token liegt im URL-**Fragment** (`/#token=…`). Fragmente werden nicht an Server geschickt
  und landen daher nicht in Zugriffslogs; `#token=` ist zusätzlich ein Redactor-Muster aus A10.

### Nur sichere Verbindung

- Erlaubt: `https://…` oder Loopback (`localhost`, `127.x`, `::1`).
- Abgelehnt: `http://192.168.x.x`, `http://10.x`, jede nicht-http(s)-URL, URLs mit Zugangsdaten.
- Steht ein Proxy davor, wird `X-Forwarded-Host` **nur mit** `X-Forwarded-Proto: https` übernommen;
  ein http-Proxy fällt nicht still auf Loopback zurück.
- Eine öffentliche Adresse entsteht ausschließlich durch explizites `CONNECT_MOBILE_BASE_URL`
  (Stefans Freigabe). Ohne diese Variable bleibt alles lokal.
- Schreibende Routen prüfen den `Origin` (Same-Origin); fremder Origin → **403**.

### Weitere Eigenschaften

- Token: 32 Byte `randomBytes`, base64url; gespeichert nur SHA-256.
- Einmal-Verwendung: nach dem Einlösen wird das Ticket entfernt; zweiter Versuch → **404**.
- Höchstens 5 offene Codes; darüber **429** mit klarer Meldung.
- Geräte-Credential: 32 Byte, nur Hash auf Platte, wird **einmal** an das Handy ausgeliefert.
- Abmelden setzt `revokedAt` (kein Löschen); `/me` antwortet danach **401**.
- Kein `localStorage`/`sessionStorage`/Cookie für das Einmal-Token; es lebt nur im React-State.
- QR wird serverseitig aus der eigenen Pair-URL erzeugt (vendorter qrcode-generator, MIT);
  im Browser als `data:`-Bild gerendert, kein `dangerouslySetInnerHTML`.

## 8. Offene Wünsche an andere Lanes

### A37 — Server-Verdrahtung (blockierend für die Funktion)

1. Router mounten:
   ```ts
   import { createT3MobileRoutes } from "./t3-bridge/mobile";
   app.route("/api/t3/mobile", createT3MobileRoutes({ authMiddleware: t3Auth }));
   ```
2. **Auth-Aufteilung beachten:** `/pair/redeem` und `/me` dürfen **nicht** von einer
   Better-Auth-Session-Middleware umschlossen werden — das Handy hat keine Browser-Session.
   Die PC-Routen (`/status`, `/pair`, `/devices`, `/devices/:id/revoke`) schützt der Router
   selbst über `authMiddleware`. Wird pauschal `/api/t3/*` mit A10 umschlossen, ist die
   Handy-Kopplung unbrauchbar.
3. `CONNECT_MOBILE_BASE_URL` (optional, nur https) in `.env.example` dokumentieren; ohne die
   Variable bleibt die Kopplung lokal (Loopback).
4. Routen-Konstanten (`T3_MOBILE_ROUTES`) bei Bedarf in die A01-Verträge übernehmen — ich habe
   `contracts.ts` bewusst nicht angefasst.

### A39 — Benutzer-Menü (bereits erledigt)

A39 hat den Einstieg während meiner Arbeit bereits eingehängt (`app-sidebar.tsx`): Import von
`PhoneT3Dialog`, State `phoneOpen`, Menüpunkt „Handy verbinden" (bei Flag an öffnet der Dialog,
sonst weiter `/settings#handy-verbinden`) und `<PhoneT3Dialog … />` am Ende. Der App-Typecheck
bleibt danach bei denselben 17 vorbestehenden Fehlern, **0 in `phone-t3/**`**.

Optional bleibt eine Route `/phone`, die `#token=` aus dem Fragment liest und per

aktuell auf `/`.

### A11/A12 — Agenten wirklich vom Handy steuern

Das Geräte-Credential ist vorhanden und über `GET /api/t3/mobile/me` prüfbar. Damit das Handy
Nachrichten senden und streamen kann, müssen `/api/t3-agents/:id/messages` und `/stream` das
Credential (`Authorization: Bearer …`, serverseitig über `MobilePairingService.authenticate`)
akzeptieren — oder A37 entscheidet, dass das Handy die normale Better-Auth-Session nach dem
Einlösen nutzt. Das ist außerhalb meiner Lane und der letzte fehlende Funktionsbaustein.

  `apps/app/src/lib/t3/contracts.ts` aufnehmen (nur A01).
- Prüfen, ob ein eigenes Flag `connect.t3.mobile` gewünscht ist. Aktuell hängt alles an
  `connect.t3.bridge` (Default aus = altes Verhalten).

## 9. Risiken

| Risiko | Bewertung / Gegenmaßnahme |
|---|---|
| Ohne A37-Mount liefert die API 404 | Erwartet; Panel zeigt eine verständliche Fehlermeldung, Flag aus bleibt altes Verhalten. |
| Host-Header-Manipulation / DNS-Rebinding | QR nutzt die Anfrage-Origin; HTTPS + Same-Origin + Auth begrenzen das. Eine feste `CONNECT_MOBILE_BASE_URL` ist die sichere Variante für öffentliche Adressen. |
| Kein Rate-Limit pro IP | Nur max. 5 offene Codes; für zusätzlichen Schutz wäre A37/Rate-Limiter zuständig. |
| Server-Neustart verwirft offene Codes | Gewollt (kurzlebig, kein Klartext auf Platte). Gekoppelte Geräte bleiben erhalten. |
| Datei `devices.json` | Enthält nur Hashes und Metadaten; Schreibfehler werden geloggt, nicht geworfen. Pfad liegt im bestehenden `ConnectAgents`-Ordner. |
| Öffentliche Erreichbarkeit | Ohne Stefans `CONNECT_MOBILE_BASE_URL` + HTTPS wird nichts nach außen geöffnet. T3-Sidecar bleibt unberührt. |
| Handy-Credential im App-Speicher | Liegt außerhalb dieser Lane; das Handy muss es sicher ablegen. Serverseitig ist nur der Hash bekannt. |
| Live-Kopie | Nicht angefasst. Einspielen und Neustart von Port 3101 ausschließlich A40 nach Stefans OK. |
