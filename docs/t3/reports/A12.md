## 1. Ziel und Umsetzung in einem Satz

Der Hub streamt die von A06 übersetzten `ConnectChatEvent`s als SSE in den Connect-Chat, gibt
**nur sichtbaren** Chats Text-Deltas, fasst Deltas zusammen, hält **20 Events/s je Chat** hart ein,
sendet alle 15 s einen Heartbeat und erlaubt nach einem Verbindungsabbruch die Wiederaufnahme ab
`Last-Event-ID`; alle übrigen Agenten melden ausschließlich Status über einen eigenen Stream.

## 4. Architektur und Entscheidungen

### 4.1 Hub statt Logik in der Route

Die Route kennt nur HTTP: Frame senden, aufräumen. Sichtbarkeit, Budget, Coalescing, Id-Vergabe und
Wiederaufnahme liegen im `T3StreamHub`. Dadurch ist der Kern ohne Server testbar (alle Tests laufen
gegen den Hub, die Routentests nur gegen die SSE-Hülle).

### 4.2 Sichtbarkeit (Aufgabe 2)

Ein Chat gilt als sichtbar, solange mindestens ein SSE-Abonnent hängt — plus **5 s Nachsicht**
(`unseenGraceMs`), damit ein Browser-Reload die Verbindung ohne Lücke wieder aufnimmt. Der Hub meldet
der Quelle `setVisible(agentId, true/false)`; `T3ThreadSource` abonniert den T3-Thread **nur** dann.
Unsichtbare Chats:

- bekommen **kein** `text_delta`, `tool`, `plan`, `approval` usw. (Events werden verworfen, kein
  Speicherwachstum),
- erscheinen aber im Status-Stream (`running`, `queued`, `waiting_approval`, `idle`, `error`),
- erzeugen keine Upstream-Last.

### 4.3 Budget (Aufgabe 3)

`SlidingWindowBudget` kombiniert zwei Bedingungen:

1. **gleitendes 1-s-Fenster:** in jedem 1000-ms-Fenster höchstens 20 Events,
2. **Mindestabstand** `ceil((1000+1)/limit)` ms (bei 20/s: 51 ms).

Der Mindestabstand ist nötig, weil ein reines Fenster 20 Events auf einmal ausschütten und im
nächsten Fenster erneut senden dürfte — über 1,5 s wären das 40 Events (26,7/s). Die zusätzliche
Millisekunde verhindert außerdem den Grenzfall, dass 20 Events mit exakt 50 ms Abstand an einer
Fenstergrenze als 21 Events im selben 1000-ms-Fenster liegen. Mit Abstand liegt die gemessene Rate
stabil unter dem Limit.

### 4.4 Coalescing

- Text-Deltas werden bis `coalesceMs` (50 ms) gesammelt und als **ein** `text_delta` mit
  verkettetem Delta gesendet.
- Kommt ein Nicht-Text-Event, wird der Textpuffer vorher geflusht (Reihenfolge bleibt korrekt).
- Tool-/Plan-/Subagent-Events desselben Items ersetzen ein noch **gepuffertes** Event; bereits
  gesendete Events bleiben unverändert (A22 ersetzt die Zeile über die stabile Item-Id).
- Approval-Karten desselben `requestId` ersetzen sich; `usage` wird auf den letzten Stand verdichtet.

### 4.5 Wiederaufnahme (Abnahmekriterium)

Jedes ausgelieferte Event erhält eine je Chat monotone `id` und landet im Ringpuffer
(`logSize` 512). Beim Verbinden liest die Route `Last-Event-ID` (Header) oder `?lastEventId=`:

- Id vorhanden und gedeckt → `replay` genau der fehlenden Events, dann live,
- Id älter als der Puffer → `resync` mit `reason: "log_gap"`,
- Id unbekannt (z. B. nach Serverneustart) → `resync` mit `reason: "unknown_event_id"`.

Zwischen Aufbau und `activate()` eintreffende Events werden gepuffert; es gibt keine Lücke und keine
Dublette. Der Client lädt bei `resync` den Thread-Snapshot (A11).

### 4.6 Status-Stream (Aufgabe 2, zweite Hälfte)

`GET /api/t3/status-stream` sendet **gebündelte Snapshots** (alle Agenten in einem Event), höchstens
2 pro Sekunde, plus Heartbeat. Ein Test erzwingt, dass weder Prompts noch Tool-Ausgaben, Dateinamen
oder `text_delta` im Snapshot landen. Status werden abgeleitet aus:

- `hub.publish(...)` (läuft/ wartet auf Freigabe/ Fehler/ fertig),
- `hub.reportStatus(agentId, state, meta)` — für Warteschlange/Provider aus A08/A11/A36,
- `T3ThreadSource` bei fehlender Thread-Zuordnung (`error` mit Begründung).

**Wichtig für die Verdrahtung:** Da unsichtbare Chats stromaufwärts nicht abonniert sind, können
deren Zustände nur aus `reportStatus` kommen. A08/A11 sollten ihre Zustandswechsel in den Hub melden
(siehe Wünsche).

### 4.7 Quelle (A03 + A06)

`T3ThreadSource` nutzt `T3RpcClient.subscribeThread` (A03) und `translateEvent`/
`makeTranslatorContext` (A06), je Agent mit eigenem Übersetzer-Kontext. Das Thread-Verzeichnis ist
ein Port:

```ts
createThreadMapDirectory(store) // nutzt IThreadMapStore.getActiveThread (A11)
```

Ohne Zuordnung wird **nicht geraten**: Status `error` mit „Kein T3-Thread für diesen Agenten“.
Für A37 gibt es `createT3ThreadSource({ client, directory })`.

### 4.8 Feature-Flag

Alle Routen liegen hinter `connect.t3.bridge` (A01). Zusätzlich prüft die A10-Middleware Flag und
Session. Flag aus → **404**, ohne Session → **401** (beides getestet). Ohne angehängte Quelle
liefert der Hub nur Status/Heartbeats und niemals erfundene Chat-Events.

## 5. Routen und Wire-Format

| Route | Zweck |
|---|---|
| `GET /api/t3-agents/:agentId/stream` | Chat-Events (A01-Vertrag `T3_ROUTES.stream`) |
| `GET /api/t3/agents/:agentId/stream` | Alias entsprechend der Aufgabenstellung |
| `GET /api/t3/status-stream` | Status-Snapshots (nicht in A01s `T3_ROUTES` enthalten, siehe Wunsch 2) |

Chat-Stream (SSE):

```text
event: ready     data: { type:"ready", stream:"chat", agentId, lastEventId, resumed, retryMs, at }
event: chat      data: { id, agentId, at, event }        // event = ConnectChatEvent (A01/A06)
event: resync    data: { type:"resync", agentId, reason, requestedLastEventId, lastEventId, oldestAvailableId }
event: keepalive data: { type:"keepalive", at }          // alle 15 s, zusätzlich ": hb <iso>"
```

Status-Stream:

```text
event: ready     data: { type:"ready", stream:"status", agentId:null, ... }
event: status    data: { type:"status", seq, at, agents:[{agentId,state,queuePosition,provider,detail?,changedAt}] }
event: keepalive data: { type:"keepalive", at }
```

`id:` steht nur auf `chat`-Frames; `EventSource` sendet ihn automatisch als `Last-Event-ID`.

## 9. Offene Wünsche an andere Lanes

1. **A37 (Server-Verdrahtung):** Stream-Routen unter `/api` einhängen und die Quelle anhängen:

   ```ts
   import { registerT3StreamRoutes, createT3StreamRoutes } from "./t3-bridge/routes/stream";
   import { getT3StreamHub, createT3ThreadSource, createThreadMapDirectory } from "./t3-bridge/stream";

   app.route("/api", createT3StreamRoutes());          // oder registerT3StreamRoutes(app)
   getT3StreamHub().attachSource(
     createT3ThreadSource({ client: t3RpcClient, directory: createThreadMapDirectory(threadMapStore) }),
   );
   ```

   Bitte **nicht doppelt** mounten (die Datei registriert beide Chat-Pfade selbst). Ohne
   `attachSource` gibt es nur Status/Heartbeats, keine Chat-Events.

2. **A01 (Verträge):** `T3_ROUTES` um `statusStream: "/t3/status-stream"` ergänzen und die
   Wire-Typen `StreamReady`, `StreamResync`, `StreamStatusSnapshot`, `StreamAgentStatus` in beide

   in §7 (`/api/t3-agents/...`) und im Auftrag (`/api/t3/agents/...`) unterschiedlich — A12 bedient
   beide; eine Festlegung wäre gut.

3. **A11 (Threads):** `IThreadMapStore` wird über `createThreadMapDirectory` gelesen. Wünschenswert:
   Bei Kontextrotation (A15) den offenen Stream informieren (`notifyResync` + neues Thread-Abo),
   sonst läuft ein offener Chat bis zum Verlassen auf dem alten Thread weiter.

4. **A08/A11/A36 (Status):** Für **unsichtbare** Agenten kann der Hub keinen Upstream-Status sehen.
   Bitte Zustandswechsel über `getT3StreamHub().reportStatus(agentId, state, { queuePosition,

   `lastEventId` aus den `chat`-Frames merken (EventSource macht das automatisch). Ein

## 10. Risiken und Grenzen

1. **Budget gilt je Chat, nicht je Browser-Tab.** Zwei Tabs auf demselben Chat erhalten je 20/s
   (zusammen 40/s). Das entspricht der Vorgabe „je Chat“; bei Bedarf kann A12 später je Verbindung
   drosseln.
2. **Initialer Status-Snapshot** wird je Verbindung sofort gesendet und nicht auf das 2/s-Budget
   angerechnet. Bei sehr vielen gleichzeitigen Status-Tabs steigt die Last entsprechend der
   Verbindungszahl; der Snapshot ist bewusst gebündelt.
3. **Wiederaufnahme ist prozesslokal.** Nach einem Serverneustart ist der Ringpuffer leer → die
   Route sendet `resync`, der Client lädt den Snapshot (A11). Das ist beabsichtigt, es wird nichts
   geraten.
4. **Warteschlange hat eine Notbremse** (`maxOutbox` 256): Bei anhaltender Überlast werden zuerst
   zusammenfassbare Events verworfen (`dropped`-Zähler in `chatStats`), nie stillschweigend
   `turn_end`/`error`, solange Alternativen existieren.
5. **Status-Flackern:** Abgeleitete Zustände (z. B. `running` aus `usage`) können von expliziten
   Meldungen abweichen. Der Status-Stream bündelt, sodass der Browser nur den letzten Stand sieht.
6. **Quelle ohne Sidecar:** Ohne angehängte Quelle bleibt der Chat leer (nur `ready`/Heartbeat).
   Das ist die gewünschte „kein Fallback“-Regel, sollte in der UI aber als „nicht verbunden“
   erscheinen (A21/A23).
