### 1.1 Aufgabe 1 — `runtime === "t3"` → `t3-agent-chat` (A22)

`channel-chat.tsx`:

* Neu: `resolveAgentRuntimeKind({ serverRuntime, profile })` aus `agent-shell.ts` liefert genau eine
  von drei Antworten: `"cloud" | "t3" | "cli"`.
  * `"cloud"` hat Vorrang — ein Cloud-Agent (Muse) läuft beim Anbieter und darf **nie** still über
    eine CLI antworten.
  * `"t3"` nur, wenn `getT3Flag("bridge")` gesetzt ist und der Agent entweder vom Server als `t3`
    gemeldet wird oder eine Engine mit T3-Treiber hat (`codex`, `claude`, `cursor`, `grok`,
    `freebuff`, `antigravity`, `chatgpt`).
  * Alles andere bleibt `"cli"` — der bisherige Chat, unangetastet.
* Neu: `const isT3Chat = runtimeKind === "t3";`
* Render-Zweig: `{isT3Chat ? <T3AgentChat … /> : <bisheriger Chat/Cloud-Chat …>}`.
  Der Server liefert heute ohnehin nur `"cloud"` oder `"cli"`; `t3` entsteht im Client aus dem Profil,
  solange der Server es nicht meldet (siehe Wunsch an A37 unter Punkt 6).
* `deliver`: im T3-Fall geht der Text über `sendT3Message(runtimeAgentId, { clientMessageId, text, provider })`
  an `/api/t3-agents/:agentId/messages`; die Antwort läuft über den SSE-Stream in `T3AgentChat`
  zurück. Fehler werden in `runError` gesetzt und geworfen, damit der Composer den Text zurückgibt.

**Wichtig für die Regression:** Cloud-Agenten (Muse) sind über `runtimeKind === "cloud"` nie
betroffen — der Zweig ist hinter `isT3Chat` und damit hinter dem Flag.

## 7. Risiken

1. **Clientseitige T3-Erkennung.** Solange der Server kein `"t3"` meldet, erkennt A38 den T3-Weg aus
   `engine.kind` bzw. `chosenCli`. Ein Agent mit T3-fähiger Engine, dessen Nutzer den alten Weg
   will, nimmt bei gesetztem `bridge`-Flag automatisch die T3-Brücke. Das ist gewollt (Flag = „T3
   benutzen“), aber es ist eine Verhaltensänderung, sobald `bridge` an ist — der Grund, warum beide
   Flags per A01 aus sind.
2. **Zwei Auswahl-Trigger im Composer.** Mit `cliSwap` an erscheint der T3-Selektor zusätzlich neben
   Browser-Modus und MCP-Button. Er ersetzt dort nichts, weil es dort vorher nichts gab. Wer
   „genau dieselbe Stelle“ streng als „ersetzt den bisherigen Trigger“ liest, ist im **Modell-Picker**
   (Agent-Einstellungen) bedient — dort ist es ein echter 1:1-Tausch. Falls Stefan im Chat-Kopf
   stattdessen einen vorhandenen Trigger getauscht haben will, braucht es die exakte Stelle (im
   Chat-Kopf gibt es derzeit keinen CLI-Trigger).
3. **Parallelität der Wahrheiten.** Bei aktivem T3-Chat zeichnet `T3AgentChat` den eigenen
   Verlauf. Der alte `ConversationView`/`ChatTranscript`-Zweig bleibt für Nicht-T3-Bots. Es gibt
   also zwei Chat-Implementierungen — Fehler in der T3-Branch betreffen nur T3-Bots.
4. **`sendT3Message` dynamisch importiert.** In `channel-chat.tsx` und `agent-cli.ts` wird die
   T3-Client-Bibliothek per `await import("@/lib/t3")` geladen. Das hält den Legacy-Bundle-Pfad
   frei, macht aber den Fehlerfall „Modul fehlt“ zu einem Laufzeitfehler statt eines Buildfehlers.
   Der Build prüft das nicht — bei fehlender Datei bricht erst der Turn ab.
5. **Queue-Semantik bei T3.** `dispatchT3Bridge` markiert den Eintrag als „angenommen“; die Antwort
   landet im Chat, nicht in der Warteschlangen-Ansicht. Wer den Terminal-Verlauf (`AgentCliTerminal`)
   liest, sieht dort weiterhin den alten Stand.
